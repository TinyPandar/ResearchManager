# Research Workflow

ResearchManager 采用“薄全局合同 + 按需 skill”的工作方式。主 Agent先判断当前请求属于规划、数据、实现还是实验，再只加载完成该任务需要的工作流。

## 1. 判断任务边界

收到请求后先识别目标、已知合同和完成标准。

- **直接执行**：只读调查、诊断、小修复、文档、已确认范围内的代码与测试。自行补全常规细节，持续做到完成。
- **需要 Draft Plan**：研究问题、方法、数据语义、核心接口、评价标准或实验边界将发生实质变化。
- **需要再次确认**：执行会产生未被当前请求授权的高成本、不可逆或破坏性外部动作。

不要为了流程完整而给低风险任务强加计划门禁。

## 2. 调查与 Draft Plan

缺少事实时优先进行只读调查。只有会影响关键决策的未知信息才向用户提问；其他常规假设应明确写出并继续推进。

需要 Draft Plan 时，至少说明：

- 目标、非目标和成功标准；
- 数据、输入输出、shape/坐标等接口合同；
- 方法或架构选择及关键假设；
- 验证、基线和对照实验；
- 资源、风险、停止条件与完成定义；
- 需要哪些角色以及可并行的部分。

用户已经明确要求实施某一方案时，不再机械要求二次确认；只有新增的重大边界变化才重新讨论。

## 3. Skill 路由与委派

优先使用 `.agents/skills/` 中最窄的匹配工作流：

- `research-planning`：定义或改变研究方案；
- `research-data`：数据与标注合同、生成、版本和验证；
- `research-implementation`：代码、模型、配置、Pipeline 与测试；
- `research-experiment`：正式运行、监控、checkpoint 与实验归档。

一个请求可以依次触发多个 skill，但不要因为“多 Agent”本身而增加角色。边界清楚、输出独立的工作可并行；会改同一文件、同一数据版本或同一外部任务的工作应串行。

## 4. 数据交付

需要新数据或改变数据语义时，由数据工作流先验证合同，再用真实项目流水线生成小样；必要时确认后再创建新数据版本。输出应可定位、可验证、可追溯，默认不覆盖旧版本。

## 5. 实现与验证

实现工作流在既定合同内修改模型、代码和配置，并运行与改动风险相匹配的验证。低影响、可逆变更不需要为了形式补无价值测试；涉及接口、shape、数值行为或训练逻辑时，应执行有意义的单元、集成或真实尺寸 smoke test。

测试通过后，除非出现新失败或未解决风险，不重复扩大验证范围而阻塞任务完成。

## 6. 正式实验

正式实验前核对代码版本、配置、数据版本、资源和停止条件。每个独立 run 至少固化：提交 SHA、配置、数据版本、随机种子、启动命令、平台任务 ID（如有）、输出/日志路径和 checkpoint。

若用户当前请求已经明确要求启动该实验，且资源/成本边界清楚，可直接执行；否则昂贵、长时间或占用共享稀缺资源的运行应先确认。

## 7. 结果与迭代

主 Agent基于可验证证据汇总结果，明确区分观察、推断和结论，并与基线或预期比较。失败结果保留并标记原因，不包装成成功；新的研究假设进入下一轮规划，而不是由执行角色静默改动研究问题。

## 完成定义

一项工作只有在适用范围内满足以下条件才算完成：目标产物已生成或修改；必要验证已运行；发现的问题已处理或形成明确阻塞；路径、版本、命令等复现信息可定位；限制与剩余风险已说明；需要持久化的记录已更新。
